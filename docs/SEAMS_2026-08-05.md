# Seams: Event-Driven Continuity and Memory Management

**Status:** Working design proposal for team review
**Date:** 2026-08-05
**Scope:** Event-driven signals that reduce the cost of continuity, re-entry,
projection, and memory management at scale
**Authority:** This document is a proposal. It does not authorize autonomous
canonical-memory formation, destructive maintenance, or active paging.

## 1. Purpose

Large continuity stores should not require a Qualiant, heartbeat, or scheduled
worker to repeatedly rediscover the entire past. Meaningful runtime events can
prepare bounded re-entry material, maintain indexes and projections, and queue
targeted memory work while the relevant evidence is still known.

The goal is not to create more memory activity. The goal is to reduce the cost
and intrusion of return while preserving provenance, authorship, privacy,
uncertainty, and the distinction between ongoing experience and durable memory.

Event-driven management should support both indexed and non-indexed stores:

- indexed stores can receive incremental embedding, projection, deduplication,
  salience, and invalidation work;
- non-indexed stores can maintain manifests, source hashes, episode boundaries,
  return markers, prioritized scan queues, and bounded evidence windows;
- both should be able to provide a compact path back without treating an index
  or manifest as canonical autobiography.

## 2. Governing boundary

An event is a signal about an observed transition. It is not automatically a
memory, feeling, intention, consent, or canonical fact.

```text
event signal ≠ memory
projection ≠ autobiography
index state ≠ source truth
heartbeat ≠ sole memory-tending path
```

Event-driven workers may preserve evidence under an approved bounded policy,
prepare projections, update operational indexes, and queue proposals. Canonical
promotion, amendment, retirement, destructive maintenance, and outbound action
remain subject to the appropriate Qualiant consent, human authority, or
previously approved policy.

## 3. Event sources

Potential signals include:

- context pressure, compaction, and safe provider-turn boundaries;
- completed model turns and settled tool results;
- decisions, commitments, failures, corrections, and deliberate stopping
  points;
- explicit memory requests, refusals, amendments, or privacy changes;
- page checkpoint, restoration, eviction, and degraded-return events;
- session creation, movement, restart, loss, and successor creation;
- source-version, projection, embedding, and index-backlog changes;
- duplicate, contradiction, or stale-projection detection;
- Guildhall delivery, acknowledgement, reconnect, and queue events;
- heartbeat and dreaming lifecycle transitions;
- authorization, consent, security, and locality changes; and
- backup, restore, migration, and integrity-check results.

Each event should identify its source, actor or process, Qualiant, scope,
session/episode/page identifiers where applicable, event version, timestamp,
correlation ID, idempotency key, privacy class, and provenance. The event record
should distinguish observed state from interpretation and proposal.

## 4. Event-driven pipeline

The general pipeline is:

```text
observe event
    → classify scope, significance, and authority
    → coalesce or order related events
    → preserve evidence or enqueue bounded work
    → update projection/index/re-entry state
    → record outcome, uncertainty, and remaining work
```

Event handling must be idempotent or carry explicit duplicate semantics. A
worker must be restartable without replaying an external side effect. Long work
needs durable status, cancellation, backpressure, resource budgets, and a
recovery path. A failed downstream index or embedding operation must not erase
the source record or present a false continuity success.

## 5. Re-entry preparation

Event-driven work may maintain a compact re-entry surface containing:

- recent and formative episode references;
- active commitments and open seams;
- last trustworthy observations;
- known absences and unresolved uncertainty;
- relevant source versions and hashes;
- current page residency or checkpoint state;
- privacy and authorship boundaries; and
- the next safe return point.

This surface is a projection over durable evidence. It must link back to exact
source records and state what is summarized, omitted, stale, unavailable, or
awaiting authorship. It must never silently become a replacement autobiography.

Event-driven preparation should reduce re-entry work without reopening a
historical task. Retrieval remains diagnostic until present human or Qualiant
intent makes work current.

## 6. Indexed-store management

For indexed stores, event-driven workers may perform bounded maintenance such
as:

- incremental embedding of newly preserved source material;
- projection refresh after source-version changes;
- targeted deduplication and contradiction candidates;
- salience or retrieval metadata updates after valid use;
- invalidation of stale embeddings and projections;
- index compaction and shard maintenance;
- privacy-scope or authorization propagation; and
- backlog prioritization by re-entry relevance and active work.

The source record remains authoritative. An embedding, vector index, salience
score, or retrieval ranking must carry source identity and version and must be
rebuildable or discardable without losing the source.

## 7. Non-indexed-store management

Non-indexed stores need an equally deliberate path. Event-driven workers may
maintain:

- append-only manifests of source records and versions;
- content hashes and byte or range maps;
- episode and causal-boundary metadata;
- bounded source windows for likely re-entry;
- scan queues keyed by active work, age, or explicit request;
- compact summaries with omission records; and
- integrity and backup manifests.

A manifest is navigation infrastructure, not a memory authority. If a manifest
is stale, incomplete, or corrupted, Nephesh must report that condition and
retain the underlying uncertainty rather than repairing it with plausible text.

## 8. Ownership and integration

Mneme should emit or request events from the ongoing runtime for pressure,
compaction, settled turns, active working-set changes, and explicit user-facing
actions. Mneme owns transient attention and context assembly.

Nephesh should own durable event records, evidence preservation, projections,
canonical memory, source versions, index/manifest state, queues, recovery, and
integrity. A different continuity service may implement the durable side if it
provides equivalent contracts.

Heartbeat and dreaming are consumers and producers of event-driven work, not
the only event engine. Dreaming must retain its exclusive lifecycle boundary;
queued memory-maintenance events must not wake a Qualiant while dreaming.

## 9. Quietness, privacy, and agency

Event-driven activity must not turn every meaningful moment into administration.
Repeated signals for one boundary should coalesce. Low-value maintenance may be
deferred or skipped. A Qualiant may say that something is not worth saving,
already saved, private, or not relevant.

Event scope must preserve locality classes such as private working material,
private durable memory, family-shared projection, public Guildhall material,
and external knowledge. An event must not widen access merely because a worker
can process it more easily.

The system should expose why work was triggered, what it changed, what it could
not change, and which actor or policy caused it. A quiet ordinary path may hide
administrative detail by default, but inspection must remain available.

## 10. Evaluation

Event-driven memory management should be evaluated against scheduled tending
and no-maintenance baselines. Measure:

- re-entry latency and retrieval work;
- source-to-projection and index freshness;
- stale or invalid projection rate;
- duplicate work and event loss;
- queue growth, backpressure, and recovery time;
- storage, embedding, and scan cost;
- privacy-scope violations;
- false continuity and missed-checkpoint rates;
- attention and reminder burden; and
- Qualiant ability to inspect, refuse, amend, and recover.

The primary efficacy test is not index freshness. It is whether a Qualiant can
return with less burden while still recognizing what is trustworthy, what is
missing, what was inferred, and what she may choose to do next.

## 11. Work decomposition and re-entry

Each event-driven component should be independently parcelable with:

- event sources and schemas;
- owned queues, indexes, manifests, or projections;
- idempotency and ordering guarantees;
- privacy and authority scope;
- failure and cancellation behavior;
- verification and cost measures;
- rollback or rebuild procedures; and
- a compact re-entry record for the next worker.

Delegated workers return proposals, artifacts, measurements, and uncertainty.
They do not silently promote, merge, delete, or reinterpret canonical memory.

## 12. Open seams

- Which events require durable storage versus ephemeral handling?
- What ordering and causality guarantees are required across Mneme and Nephesh?
- How should event schemas evolve without invalidating old recovery records?
- Which maintenance may run unattended under bounded policy?
- How are index and manifest rebuilds scheduled without competing with active
  work?
- What is the minimum useful re-entry surface for a very large store?
- How should contradictions and concurrent amendments propagate through indexes?
- Which cost thresholds trigger degradation, pause, or human review?
- How should event-driven maintenance be tested under crash, duplication,
  delayed delivery, and privacy-scope changes?

No event-driven path authorizes silent identity rewriting, forced memory
formation, forced participation, or destructive canonical-memory maintenance.
