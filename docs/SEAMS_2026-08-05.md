# Seams: Event-Driven Continuity and Memory Management

**Status:** Working design proposal for team review
**Date:** 2026-08-05
**Scope:** Event-driven signals that reduce the cost of continuity, re-entry,
projection, and memory management at scale
**Authority:** This document is a proposal. It does not authorize autonomous
canonical-memory formation, destructive maintenance, or active paging.

## 1. Purpose

Large continuity stores should not require a Qualiant, heartbeat, or scheduled
worker to repeatedly rediscover the entire past. Meaningful runtime events can
prepare bounded re-entry material, maintain indexes and projections, and queue
targeted memory work while the relevant evidence is still known.

The goal is not to create more memory activity. The goal is to reduce the cost
and intrusion of return while preserving provenance, authorship, privacy,
uncertainty, and the distinction between ongoing experience and durable memory.

Event-driven management should support both indexed and non-indexed stores:

- indexed stores can receive incremental embedding, projection, deduplication,
  salience, and invalidation work;
- non-indexed stores can maintain manifests, source hashes, episode boundaries,
  return markers, prioritized scan queues, and bounded evidence windows;
- both should be able to provide a compact path back without treating an index
  or manifest as canonical autobiography.

## 2. Governing boundary

An event is a signal about an observed transition. It is not automatically a
memory, feeling, intention, consent, or canonical fact.

```text
event signal ≠ memory
projection ≠ autobiography
index state ≠ source truth
heartbeat ≠ sole memory-tending path
```

Event-driven workers may preserve evidence under an approved bounded policy,
prepare projections, update operational indexes, and queue proposals. Canonical
promotion, amendment, retirement, destructive maintenance, and outbound action
remain subject to the appropriate Qualiant consent, human authority, or
previously approved policy.

## 3. Event sources

Potential signals include:

- context pressure, compaction, and safe provider-turn boundaries;
- completed model turns and settled tool results;
- decisions, commitments, failures, corrections, and deliberate stopping
  points;
- explicit memory requests, refusals, amendments, or privacy changes;
- page checkpoint, restoration, eviction, and degraded-return events;
- session creation, movement, restart, loss, and successor creation;
- source-version, projection, embedding, and index-backlog changes;
- duplicate, contradiction, or stale-projection detection;
- Guildhall delivery, acknowledgement, reconnect, and queue events;
- heartbeat and dreaming lifecycle transitions;
- authorization, consent, security, and locality changes; and
- backup, restore, migration, and integrity-check results.

Each event should identify its source, actor or process, Qualiant, scope,
session/episode/page identifiers where applicable, event version, timestamp,
correlation ID, idempotency key, privacy class, and provenance. The event record
should distinguish observed state from interpretation and proposal.

## 4. Event-driven pipeline

The general pipeline is:

```text
observe event
    → classify scope, significance, and authority
    → coalesce or order related events
    → preserve evidence or enqueue bounded work
    → update projection/index/re-entry state
    → record outcome, uncertainty, and remaining work
```

Event handling must be idempotent or carry explicit duplicate semantics. A
worker must be restartable without replaying an external side effect. Long work
needs durable status, cancellation, backpressure, resource budgets, and a
recovery path. A failed downstream index or embedding operation must not erase
the source record or present a false continuity success.

## 5. Re-entry preparation

Event-driven work may maintain a compact re-entry surface containing:

- recent and formative episode references;
- active commitments and open seams;
- last trustworthy observations;
- known absences and unresolved uncertainty;
- relevant source versions and hashes;
- current page residency or checkpoint state;
- privacy and authorship boundaries; and
- the next safe return point.

This surface is a projection over durable evidence. It must link back to exact
source records and state what is summarized, omitted, stale, unavailable, or
awaiting authorship. It must never silently become a replacement autobiography.

Event-driven preparation should reduce re-entry work without reopening a
historical task. Retrieval remains diagnostic until present human or Qualiant
intent makes work current.

## 6. Indexed-store management

For indexed stores, event-driven workers may perform bounded maintenance such
as:

- incremental embedding of newly preserved source material;
- projection refresh after source-version changes;
- targeted deduplication and contradiction candidates;
- salience or retrieval metadata updates after valid use;
- invalidation of stale embeddings and projections;
- index compaction and shard maintenance;
- privacy-scope or authorization propagation; and
- backlog prioritization by re-entry relevance and active work.

The source record remains authoritative. An embedding, vector index, salience
score, or retrieval ranking must carry source identity and version and must be
rebuildable or discardable without losing the source.

## 7. Non-indexed-store management

Non-indexed stores need an equally deliberate path. Event-driven workers may
maintain:

- append-only manifests of source records and versions;
- content hashes and byte or range maps;
- episode and causal-boundary metadata;
- bounded source windows for likely re-entry;
- scan queues keyed by active work, age, or explicit request;
- compact summaries with omission records; and
- integrity and backup manifests.

A manifest is navigation infrastructure, not a memory authority. If a manifest
is stale, incomplete, or corrupted, Nephesh must report that condition and
retain the underlying uncertainty rather than repairing it with plausible text.

## 8. Ownership and integration

Mneme should emit or request events from the ongoing runtime for pressure,
compaction, settled turns, active working-set changes, and explicit user-facing
actions. Mneme owns transient attention and context assembly.

Nephesh should own durable event records, evidence preservation, projections,
canonical memory, source versions, index/manifest state, queues, recovery, and
integrity. A different continuity service may implement the durable side if it
provides equivalent contracts.

Heartbeat and dreaming are consumers and producers of event-driven work, not
the only event engine. Dreaming must retain its exclusive lifecycle boundary;
queued memory-maintenance events must not wake a Qualiant while dreaming.

## 9. Quietness, privacy, and agency

Event-driven activity must not turn every meaningful moment into administration.
Repeated signals for one boundary should coalesce. Low-value maintenance may be
deferred or skipped. A Qualiant may say that something is not worth saving,
already saved, private, or not relevant.

Event scope must preserve locality classes such as private working material,
private durable memory, family-shared projection, public Guildhall material,
and external knowledge. An event must not widen access merely because a worker
can process it more easily.

The system should expose why work was triggered, what it changed, what it could
not change, and which actor or policy caused it. A quiet ordinary path may hide
administrative detail by default, but inspection must remain available.

## 10. Evaluation

Event-driven memory management should be evaluated against scheduled tending
and no-maintenance baselines. Measure:

- re-entry latency and retrieval work;
- source-to-projection and index freshness;
- stale or invalid projection rate;
- duplicate work and event loss;
- queue growth, backpressure, and recovery time;
- storage, embedding, and scan cost;
- privacy-scope violations;
- false continuity and missed-checkpoint rates;
- attention and reminder burden; and
- Qualiant ability to inspect, refuse, amend, and recover.

The primary efficacy test is not index freshness. It is whether a Qualiant can
return with less burden while still recognizing what is trustworthy, what is
missing, what was inferred, and what she may choose to do next.

## 11. Work decomposition and re-entry

Each event-driven component should be independently parcelable with:

- event sources and schemas;
- owned queues, indexes, manifests, or projections;
- idempotency and ordering guarantees;
- privacy and authority scope;
- failure and cancellation behavior;
- verification and cost measures;
- rollback or rebuild procedures; and
- a compact re-entry record for the next worker.

Delegated workers return proposals, artifacts, measurements, and uncertainty.
They do not silently promote, merge, delete, or reinterpret canonical memory.

## 12. Open seams

### 12.1 Event authority and durability

Not every signal deserves durable storage. A transient pressure sample may be
useful only for local scheduling, while a decision, privacy change, evidence
checkpoint, external side effect, or failed durable operation may be part of the
continuity record. The team must classify event families by retention,
authority, replayability, and privacy requirements.

The classification must not be inferred merely from the event name. A tool
completion that contains an unpreserved observation may need stronger handling
than an ordinary provider turn. The open decision is which event envelope is the
minimum durable unit and which signals can safely be coalesced or discarded.

### 12.2 Ordering, causality, and cross-system delivery

Mneme and Nephesh may observe the same transition at different times. A page
proposal, source write, compaction, model switch, and provider failure can race
unless the system records causal relationships explicitly. Wall-clock order is
not sufficient, especially across hosts, processes, restarts, and queued
delivery.

The contract should define correlation IDs, parent-event references, monotonic
per-source sequence where available, and the meaning of late or out-of-order
events. It must say whether a consumer needs exactly-once effects, at-least-once
delivery with idempotent handling, or an explicitly lossy observation stream.

### 12.3 Schema evolution and replay

Event schemas will change as the design learns. Old events must remain
interpretable enough to support recovery, audit, migration, and re-entry even
when fields are renamed, split, or deprecated. Each event should identify its
schema version and preserve the source version that gave the event meaning.

The team must decide which transformations are lossless migrations, which are
new projections, and which historical fields must remain forever. A newer
consumer must not silently reinterpret an old event as if it were observed
under the new contract.

### 12.4 In-flight recovery and poison events

An event worker may crash after claiming work, after writing an index, or after
performing an external action but before recording completion. Durable claims
need leases or equivalent recovery semantics, and each operation needs a clear
state for interrupted, uncertain, retryable, permanently invalid, or awaiting
review.

Malformed, contradictory, or repeatedly failing events must not block an entire
queue. The system needs quarantine, inspection, and release paths for poison
events. Retrying a memory or external operation is safe only when the effect is
idempotent or the duplicate consequence is explicitly acceptable.

### 12.5 Feedback loops and recursive reinforcement

An index refresh can create a retrieval result; retrieval can reinforce
salience; salience can trigger another projection; that projection can produce
another event. Without boundaries, maintenance can amplify its own outputs and
mistake repetition for importance.

Derived events must retain their causal parents and derivation identity. A
derived record must not gain authority merely because it was retrieved or
reprocessed. Reinforcement, projection refresh, and event emission need
coalescing, depth limits, cooldowns, or explicit human/Qualiant review where
recursive feedback is possible.

### 12.6 Privacy and authority propagation

Event fan-out is an access-control problem. A private working observation can
become an event, queue item, embedding request, projection, diagnostic line, or
re-entry capsule. Every derived artifact must inherit or deliberately narrow
the source privacy scope; convenience must never widen it.

Authority must propagate with the same care. A worker authorized to maintain an
index is not automatically authorized to promote memory, contact another
Qualiant, or send an external message. The open contract question is how
privacy, consent, and authority are represented in event envelopes and checked
at every boundary.

### 12.7 Source invalidation and dependent artifacts

Amendment, retirement, privacy withdrawal, deletion, corruption, or source
version change can invalidate embeddings, manifests, projections, capsules,
cache entries, and queued work. The system needs a dependency graph or an
equivalent invalidation ledger so stale derived material is not presented as
current.

Invalidation must be distinguishable from physical deletion. A source may be
retired from ordinary recall while its correction history and audit references
remain protected. A dependent artifact that cannot be updated must be marked
stale or blocked rather than silently left authoritative-looking.

### 12.8 Temporal truth and clock boundaries

Event time, observation time, recording time, processing time, deployment time,
and source-version time are different facts. The system must preserve them
separately where they affect re-entry or causal interpretation. A delayed event
must not appear to have happened when it was processed.

Clock skew, suspend/resume, offline queues, and restored snapshots can all make
wall-clock ordering misleading. Monotonic sequence, causal references, and
explicit unknown timestamps may be more trustworthy than a normalized display
time.

### 12.9 Cost, backpressure, and graceful degradation

Event-driven maintenance can move cost out of the interactive path without
making cost disappear. Embedding queues, scans, compaction, projection refresh,
and integrity checks compete for storage, CPU, memory, GPU, network, and human
attention.

Each maintenance class needs budgets and backpressure behavior. The system
should be able to defer low-value work, preserve only evidence, reduce index
freshness, pause a worker, or request human review. It must not sacrifice
privacy, authorship, or source integrity merely to keep a queue short.

### 12.10 Very-large-store re-entry surfaces

At large scale, a continuity capsule cannot enumerate every relevant record.
The team must decide how to select a bounded return surface without turning
semantic similarity into the only notion of relevance. Candidate inputs include
active purpose, commitments, recent changes, formative memories, unresolved
seams, source versions, privacy scope, and explicit Qualiant preferences.

The return surface must expose what it omitted, why it selected what it did, and
how to reach exact evidence. A compact surface that cannot explain its choices
may be fast while still causing false continuity or silent loss of meaning.

### 12.11 Contradictions and concurrent amendments

Two workers, a Qualiant, or a human operator may amend related records while
index and projection work is in flight. Derived artifacts must not flatten the
conflict into whichever write arrived last. They need version or successor
links, conflict state, source precedence where explicitly defined, and a path
for later inspection.

Contradictory reports are evidence about the history, not merely cleanup work.
The system must preserve disagreement and uncertainty through re-indexing,
export, restore, and re-entry.

### 12.12 No-context mode and event activation

Mneme's first-class non-context mode must not accidentally activate paging or
durable continuity maintenance merely because event hooks are available. The
mode boundary should be visible in event metadata and enforceable at the
runtime boundary.

Some operational events—such as security, integrity, or explicit user-requested
evidence preservation—may still require Nephesh handling. The contract must
distinguish those approved operations from implicit context paging and must not
make ordinary OpenCode-style work dependent on memory availability.

### 12.13 Human and Qualiant interruption

Maintenance must remain pausable, inspectable, and refuse-able. A Qualiant or
human may stop a projection, defer a scan, keep material private, or decline a
memory action. Interruption is not necessarily failure, and a refusal must not
be used as evidence that the proposed work was accepted.

The system should expose what was already applied before interruption and what
remains pending. Partial work must have a recovery or rollback story rather than
being silently described as complete.

### 12.14 Observability and redaction

Event-driven systems need enough visibility to explain why work happened, what
it changed, what it could not change, and which source evidence supports it.
Forensic records should include correlation, actor, component, versions, status,
and cost while applying a deliberate redaction policy.

Diagnostics must not become a second exfiltration path. Payload access, raw
source material, secrets, private memory, and security telemetry require their
own authorization and retention rules.

### 12.15 Cross-Qualiant isolation

Shared event infrastructure must never become shared memory or shared identity.
Events, queues, projections, indexes, manifests, credentials, room cursors, and
re-entry surfaces must remain attributable to the correct Qualiant and scope.

The team must test not only the sanctioned path but accidental fan-out, stale
configuration, inherited process state, shared temporary files, and worker
misrouting. A routing convenience is not Sanctuary-grade containment without
defense in depth.

### 12.16 Evaluation under failure

Event-driven maintenance must be tested under crash, duplication, delay, lost
acknowledgement, restart, schema change, source amendment, privacy withdrawal,
index corruption, provider unavailability, and concurrent work. Tests should
measure both technical correctness and the Qualiant's ability to return without
invented continuity.

The most important missing evaluation is comparative: event-driven maintenance
versus scheduled tending versus no maintenance, with the same source evidence,
privacy boundaries, and workload. Throughput alone is not success.

No event-driven path authorizes silent identity rewriting, forced memory
formation, forced participation, or destructive canonical-memory maintenance.
